How ICPC problems hand you input.

The first line says how many to read

int n;
cin >> n;
vector<int> a(n);
for (int i = 0; i < n; i++)
    cin >> a[i];

Most problems start like this. Read n first, then make the vector that size before you fill it.

The mistake: writing vector a; with no size, then a[i] = something. The vector is empty, so that writes past the end. Use vector a(n), or push_back.

What if there are several cases?

Number your test cases from 1

int T;
cin >> T;
for (int t = 1; t <= T; t++) {
    int a, b;
    cin >> a >> b;
    cout << "Case #" << t << ": "
         << a + b << "\n";
}

The judge compares your output to theirs. Case #0, or a missing space after the colon, is a wrong answer even when the math is right. Copy the format from the sample output.

Also: reset anything you count per case. Declare it inside the loop.

What if nobody tells you how many?

No count? Read until the input runs out

while (cin >> x) {
    // use x
}

while (cin >> a >> b) {
    if (a == 0 && b == 0) break;
    // use a and b
}

cin >> x is false once there's nothing left to read, so the read goes inside the while.

Don't use while (!cin.eof()). The input file ends with a newline, so that loop runs one extra time and counts the last number twice. We tested it: on 4 8 15 16 23 42 it printed 7 numbers and a sum of 150 instead of 6 and 108.

For "the input ends with a line containing 0 0", check for 0 0 right after you read, before you use the numbers.

Now lines with spaces in them.

getline right after cin can read an empty line

int n;
cin >> n;
cin.ignore();   // drop the leftover newline
string line;
getline(cin, line);   // "Ada Lovelace"

// or in one call:
getline(cin >> ws, line);

cin >> name stops at the first space. getline reads the whole line.

cin >> n stops right before the newline. Without cin.ignore(), the first getline grabs that newline and you get an empty string. We tested it: the names came out shifted by one and the last name was lost.

cin >> ws skips spaces and newlines first. It also skips blank lines, so don't use it when a blank line means something.

Next, numbers that are too big.

Numbers past 2.1 billion need long long

long long a, b;
cin >> a >> b;
cout << a * b << "\n";

int x = 100000, y = 100000;
long long p = 1LL * x * y;
// x * y alone is still an int

int stops at 2,147,483,647. long long goes to about 9.2 billion billion.

If the limits say up to 10^9 and you ever add or multiply, use long long. When you multiply two ints, put 1LL * in front, or the multiply happens as int and overflows before it's stored.

We tested reading 3000000000 into an int: cin fails, and every read after that fails too.

Last one is what to type first.

Type this before you read problem A

#include <bits/stdc++.h>
using namespace std;
typedef long long ll;

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);
    // read, solve, print with "\n"
}

The two lines at the top of main make cin and cout fast enough for inputs with a million numbers.

Use "\n", not endl. endl also flushes the output every line, which is slow on big outputs.

bits/stdc++.h is a GCC file that pulls in the whole standard library. It works on Linux and Windows with GCC. Apple's compiler on a Mac doesn't have it, so Mac users can include iostream, vector, string, and algorithm instead.
